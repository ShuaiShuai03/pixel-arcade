# Quality expansion to 100 games

**Execution policy updated by the user:** develop and test no more than three games at a time. A new batch begins only after every game in the current batch passes development, testing, independent review, and browser acceptance. The thematic packs below are roster groupings, not parallel work assignments. See [batch status](batches.json) and [acceptance gates](BATCHES.md). All simulated physical systems must obey physically consistent forces, momentum, contact, and energy changes. Any proposed fictional mechanic is provisional and must be reconciled with this requirement before implementation.

The roster contains **79 new games**, arranged in **nine packs of eight and one pack of seven**. Combined with the existing 20 JavaScript games and Pixel Parkour WASM, the result is exactly **100 playable games**.

**Final completion gate:** after all 100 games have completed development and their initial acceptance, independently review every game again against the integrated project. Conduct this second pass in groups of no more than three games. Record the reviewed source revision, evidence, findings, fixes, and final verdict for each game. Resolve and re-review all actionable findings, including regressions from shared changes. The project is complete only when all 100 games have passed this final review; initial batch acceptance does not satisfy this gate.

## Implementation plan

### Responsibilities and order

1. **Controller:** retain ownership of the catalog, launcher, fixed-step loop, shared input/audio/rendering utilities, accessibility, responsive layout, build configuration, and acceptance reporting.
2. **Existing-game owners:** repair and deepen their assigned games without replacing them with new catalog entries.
3. **New-game owners:** implement only their assigned `src/games/<id>.js` and `tests/<id>.test.js`.
4. **Controller:** integrate completed packs incrementally, verify catalog counts and metadata, and resolve shared-contract issues centrally.
5. **Independent reviewers:** inspect actual rules, physics, failure paths, and tests. A passing smoke test is insufficient.
6. **Controller:** complete keyboard and touch browser journeys, including real wins and losses, before recording acceptance.

Use the existing module boundary, `tests/harness.js`, seeded randomness, and dependency-free canvas approach. The search-first inspection found reusable test/input infrastructure already present; this plan does not require a new engine, dependency, external asset pack, or network service.

### Shared implementation requirements

- Every new game exports the documented `meta` and `createGame` interface.
- `meta.touchControls` is mandatory and contains every action needed to complete the game.
- All descriptions, action labels, status messages, objectives, and terminal messages support English and Simplified Chinese.
- Use only `action`, `arcade`, `puzzle`, or `sports` for `genre`. “Strategy,” “simulation,” and “rhythm” below are pack labels.
- Every game includes inspectable progress, resources, actor/board state, and terminal phase in `getState()`.
- Campaigns need reachable victory and failure paths. Reversible logic puzzles may have victory only and unlimited undo.
- Shared drawing, geometry, input, and timing helpers are acceptable. A shared configurable rules engine yielding cosmetic variants does not count as distinct games.
- No commercial game names, copied sprites, copied maps, copied audio, or extracted third-party implementation code.

### Control conventions

The table’s control profiles are implementation requirements:

| Profile | Keyboard                                                                           | Touch                                          |
| ------- | ---------------------------------------------------------------------------------- | ---------------------------------------------- |
| Move    | Arrows/WASD; Space primary; X secondary where specified                            | Direction buttons plus named actions           |
| Aim     | Arrows aim; hold/release Space power; X alternate                                  | Aim buttons plus press/release action          |
| Board   | Arrows select; Space confirm; Z undo; X rotate/alternate where needed              | Selectable cells plus the same named actions   |
| Rhythm  | Explicitly listed directional/action keys; no pointer dependency                   | Separate labeled pads                          |
| Dual    | P1 WASD/F/G; P2 Arrows/Comma/Period                                                | Both players’ controls independently available |
| Program | Arrows navigate; Space insert/confirm; X change instruction; Enter execute; Z undo | Matching program editor controls               |

Two-player games must also work in solo mode with an actual AI opponent, a partner-switch mechanic, or a suitable solo challenge. Do not describe a game as two-player merely because two sets of keys affect the same actor.

### Quality gates

**Rules and control feel**

- Run simulation through the controller’s fixed-step loop; keep velocity and timers in seconds.
- Holding a key must not create unintended repeated discrete actions.
- Jumping games require deliberate air control, jump buffering, coyote time where appropriate, and a documented jump envelope.
- Collision geometry must correspond to visible solids. Fast projectiles and moving obstacles must not tunnel.
- Resolve penetration without unexplained teleportation or imparting energy repeatedly.
- Detect approaching contact at the end of a simulation step, but do not count separating tangency as another impact. Recheck active contacts after a later impulse from a third body.
- Order body impacts, projectile hits, pickups, expiration, and disappearing geometry by their actual event times. A later pickup cannot undo an earlier fatal hit, and a destroyed body or part cannot consume a later shot.
- Distinguish inactive objects, damaging objects, and intentional attacks. For Snowball Siege specifically, an idle or merely touching snowball must not become a damaging moving attack.
- Input cancellation, simultaneous directions, cooldown boundaries, and action release must behave consistently.
- Resolve simultaneous attacks, detonations, and terminal outcomes without favoring a player or object because it appears first in an array.
- No immediate unavoidable damage; hazard spawning must preserve a response window.
- Test recovery from ordinary mistakes as well as optimal play: stopping at a surface boundary, resting against a solid, interrupted movement, and depleted recoverable resources must not silently remove all useful controls.

**Depth and distinctiveness**

- Each new game must implement its defining mechanic below.
- Campaigns need at least three meaningfully different stages or challenges, not only increasing speed or enemy counts.
- Include a teaching stage, a combination stage, and a mastery stage.
- Scoring must reward intended play without farming exploits.
- Resource management must support recovery rather than create silent unwinnable states.
- Every stage’s intended solution must work through public player input.

**Art and feedback**

- Distinct silhouettes and palettes; readable foreground/background separation.
- At least idle, active, and feedback states for the principal actor or equivalent board feedback.
- Environmental detail must explain play: wind flags, polarity marks, valve direction, target lanes, attack windups.
- Impacts, successful actions, damage, and completed objectives need different visual feedback.
- Essential information must remain readable at mobile display sizes.
- Never rely solely on color, sound, flashing, or particle effects to communicate a rule.

**Accessibility and touch**

- Every action is keyboard-completable and touch-completable.
- Touch buttons retain their own pointer ownership; holding one cannot release another.
- Avoid mandatory rapid tapping. Offer hold-based charging or generous timing alternatives.
- Provide a relaxed timing option for rhythm and precision challenges when it can preserve the central mechanic.
- Use symbol/shape distinctions for colored objects and clear selection/focus indicators.
- No essential canvas text smaller than the existing readable HUD scale.

**Verification**

For every game:

1. Write and run meaningful tests before implementation.
2. Test the central rule, illegal action rejection, scoring, collision/resource boundaries, and stage progression.
3. Complete at least one full victory through legal inputs; test a legal loss where the design has a loss condition.
4. Verify a new instance restores all initial state.
5. Verify terminal callback happens once and subsequent updates cannot change gameplay.
6. Run seeded simulation with finite-state and bounded-array assertions.
7. Draw meaningful early, middle, and terminal states through `mockContext()`.
8. Exercise documented keyboard controls and equivalent touch actions.
9. Review final code independently.

Use **80% coverage as a supporting threshold**, never as evidence that a game is enjoyable or correct. Record actual checks and unresolved limitations; do not claim “zero bugs” or superiority to an official game.

## Duplicate-risk review

These pairs require particular review because their themes overlap:

- **Glider Ridge / Lunar Lander / Balloon Balancer / Meteor Drift:** respectively unpowered lift and stall, powered landing with fuel, wind-layer navigation, and toroidal asteroid combat.
- **Grapnel Gorge / Tether Twins / Rescue Helicopter:** respectively swinging traversal, two-actor conductive routing, and suspended passenger handling.
- **Rail Switch / Traffic Conductor / Harbor Master:** respectively track junctions, signal conflict zones, and berth/resource scheduling.
- **Mirror Lab / Circuit Weaver:** beam reflection versus graph connectivity and electrical separation.
- **Shield Sentinel / Dash Duelist / Dungeon Dash:** directional reflection, one-on-one recovery windows, and room exploration/combat.
- **Mimic Vault / Time Sculptor:** replayed inputs versus selectively frozen world objects.
- **Pulse Forge / Echo Drums / Dance Duel:** authored note charts, delayed rhythmic recall, and rhythm-plus-counterstance competition.
- **Rooftop Hoops / Mini Links / Fortress Siege / Pocket Pinball:** shared projectile mathematics is acceptable; objectives, input, contact rules, and progression must remain separate.

Reject any delivered game that implements only a renamed version of another game’s update loop. The acceptance record should name the actual differentiating rule and the test that proves it.
